# Agent Brain v0.9.0 — Code-Aware Staleness

## Overview

When you extract knowledge from a file and the file later changes, the captured knowledge may no longer hold. v0.9.0 ships the substrate to detect this:

1. **Capture-time provenance** — `brain write --from-file path[:lines]` records sha256 + commit + branch into the source's `provenance_meta`.
2. **Staleness scans** — `brain staleness check` (whole DB) and `brain staleness diff --since <ref>` (git-diff-driven, fast) compare stored hashes against the live filesystem.
3. **Hook integration** — SessionEnd auto-runs the scan and records a `staleness_detected` event. The next session's resume bundle surfaces the count + source IDs.

Staleness is a **signal**, not an automatic mutation. The brain flags affected sources; the agent decides whether to invoke `brain-revise` or `brain.write.invalidate`. No LLM call in the scan path.

## What changed

- **Schema:** migration 014 adds `sources.provenance_meta JSONB` + GIN index on `(provenance_meta->'source_files')` for fast reverse lookup.
- **New modules:**
  - `src/brain/provenance.py` — `file_hash`, `attach_provenance`, `list_sources_for_files` (pure).
  - `src/brain/staleness.py` — `scan_db`, `scan_diff`, `StaleSource`, `StalenessReport` (pure).
- **CLI:**
  - `brain write --from-file path[:start-end]` (repeatable) attaches provenance after the INSERT.
  - `brain staleness check` — whole-DB sweep.
  - `brain staleness diff --since <ref> [--cwd <path>]` — git-diff-driven, only inspects changed files.
- **Hook:**
  - `session_end_cmd` runs `scan_db` and records `session_events(event_kind='staleness_detected')` when stale sources exist. Non-fatal — wrapped in try/except.
- **Bundle render:**
  - `BundleSelection.stale_sources` field added.
  - `gather_bundle_selection` pulls the latest `staleness_detected` event payload.
  - `render_bundle` renders a "Potentially stale sources (file changed since capture)" section when non-empty.
- **Skill:** `brain-staleness` (record/inspect surface).

## Provenance schema

```json
provenance_meta: {
  "source_files": [
    {"path": "/abs/path/to/file.py", "sha256_at_capture": "abc...", "line_range": [42, 67]}
  ],
  "commit_at_capture": "f3bf1d4...",
  "branch_at_capture": "main",
  "captured_at": "2026-05-28T10:00:00Z"
}
```

`provenance_meta` is NULL for sources captured before v0.9.0 — staleness scan silently skips those.

## Staleness scan modes

| Mode | When to use | Cost |
|---|---|---|
| `scan_db` (CLI: `brain staleness check`) | Periodic audit, after large refactors, or any time you want a full sweep | O(active sources with provenance_meta) — one stat + sha256 per referenced file |
| `scan_diff` (CLI: `brain staleness diff --since <ref>`) | After a substantive session — only the files changed since the ref are inspected | O(files-in-diff) + GIN-indexed JSONB lookups |

Both are pure read — they never mutate `sources.t_valid_to`. Mutation is the agent's job.

Status classifications:
- `changed` — file exists, current sha256 differs from `sha256_at_capture`.
- `missing` — file no longer exists at the captured path.
- `untracked` — provenance entry has `sha256_at_capture=None` (file was missing at capture time too).

## Capture-time CLI

```bash
# Single file, whole-file provenance.
brain write --kind decision --content "we use Postgres" --from-file src/db.py

# Multiple files.
brain write --kind decision --content "..." \
  --from-file src/a.py --from-file src/b.py

# Specific line range.
brain write --kind pattern --content "use sha256 not md5" \
  --from-file src/hash_utils.py:42-58
```

The commit + branch at capture time are recorded automatically from `git rev-parse HEAD` and `git rev-parse --abbrev-ref HEAD` if the cwd is a git working tree. Outside git, both stay NULL.

## Staleness CLI

```bash
# Whole-DB sweep.
brain staleness check

# Diff-based — only files changed since the given git ref.
brain staleness diff --since HEAD~1
brain staleness diff --since main
brain staleness diff --since "$(git merge-base main HEAD)"

# Explicit repo path.
brain staleness diff --since HEAD~1 --cwd /home/keertan/codes/brain
```

Output format (one line per stale source):

```
scanned 12 sources / 14 file references
3 stale source(s):
  [42] kind=decision status=changed path=/abs/path/to/file.py lines=42-67
  [78] kind=gotcha status=missing path=/abs/path/to/gone.py
  [91] kind=pattern status=changed path=/abs/path/to/other.py
```

## Triage workflow

For each stale source:

1. **Read the current file** (or its diff vs `sha256_at_capture`).
2. **Decide if the captured claim still holds.**
3. **Pick one:**
   - **Still true:** ignore. Optionally re-capture to refresh the hash.
   - **Stale:** invalidate (`brain.write.invalidate(<source_id>, reason='...')`), OR re-capture the new claim and let dedup handle it, OR invoke `agent-brain:brain-revise` for structured invalidation.
   - **Missing:** almost always invalidate — the file is gone.

## Hook integration

`SessionEnd` runs `staleness.scan_db` after the existing compliance check. When stale sources exist, it records:

```json
session_events.event_kind = 'staleness_detected'
session_events.payload = {
  "stale_count": 3,
  "scanned_sources": 12,
  "scanned_files": 14,
  "stale_sources": [
    {"source_id": 42, "kind": "decision", "path": "...", "status": "changed"},
    ...  # capped at 50 entries
  ]
}
```

`gather_bundle_selection` pulls the latest such event into `BundleSelection.stale_sources`. `render_bundle` includes a "Potentially stale sources" section in the markdown bundle injected at the next SessionStart. The agent sees the warning when resuming.

## Known limits (v0.9.0)

- **No automatic re-capture.** Brain flags; agent decides. The semantic question "does the change contradict the captured claim?" is out of scope (deferred to v0.9.1 `brain-revise --from-diff`).
- **`scan_db` is synchronous in SessionEnd.** Large brains with thousands of provenance-tagged sources will see SessionEnd latency. Mitigation in v0.9.1: switch SessionEnd to `scan_diff --since <session-start-commit>`.
- **Cross-branch staleness.** Staleness compares against the current working tree, not against `branch_at_capture`. If you `git checkout` to a branch where the file looks different, staleness will flap. Document but don't fix.
- **Non-git working trees.** `scan_diff` returns empty if `cwd` isn't a git repo. `scan_db` still works.
- **Relative paths not supported.** `--from-file` records the path verbatim. Use absolute paths in CI/scripts; the CLI doesn't auto-`abspath` (yet).
